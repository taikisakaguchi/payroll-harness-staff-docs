導入編

顧問先にハーネスを初めて展開するときの手順

新しい顧問先の給与計算をハーネスに乗せるときの進め方です。所長がフォルダと仕組みを用意し、担当スタッフがヒアリングから運用開始までを進めます。項目ごとのタブで読めます。

まずこれだけ

  1. 流れは 事前確認 → 準備（所長）→ ヒアリング → 会社設定 → 従業員台帳 → バックテスト → レビュー → 運用開始 の8段階。
  2. スタッフの担当はヒアリング以降ほぼ全部。会社設定（config）も CC に頼んで自分で進めてよい。迷う値だけ所長へ。
  3. 「完了」は言葉ではなく事実で判定する。バックテスト月の🔴ゼロ、確認事項の回答済み、承認記録あり、が揃ったら運用開始。

事前確認 — Go/No-Go の4項目

担当: 所長＋スタッフ（顧問契約の情報や先方への確認で埋める）

ハーネスには既知の制限があります。次の4つは最初に確認し、当てはまるものがあれば所長へ報告してから進めます。

#確認することハーネス側の事情
0-1給与システムはオフィスステーション給与か取込テンプレと支給控除一覧表の仕様が OS給与前提。他社なら所長へ明示報告
0-2社保料の控除は翌月控除か当月控除は未対応。当月控除ならエンジン側の対応が先
0-3変形労働時間制はあるか（1ヶ月単位／1年単位／シフト制）枠の突合は未実装。ありなら、実装が先か当面手動確認かを所長が判断
0-4勤怠ツールは何か。CSV等で出せるか勤怠取込の入力形式が決まる。紙・Excel なら入力動線の設計が別途必要（樹尚会の例: KOT CSV＋手修正PDF）

報告義務: 「会社設定（config）を足すだけでは済まず、エンジンの拡張が必要」と分かった時点で、黙って進めず所長へ報告します。これは §5.5 の決まりです。

準備 — フォルダと仕組みの配布

担当: 所長（スタッフはこの段階では待つ。終わったら確認だけ）

所長が開発正本から配布スクリプトでハーネスを配置します。手作業のコピーはしません。1社1フォルダで、法人が複数ある顧問先は法人ごとに台帳を分けます（例: 樹尚会／コンタクト、Nwork／Kwork）。

できあがるもの（スタッフの確認ポイント）

  • 顧問先フォルダの 07.給与・賞与 に CLAUDE.md がある（ここで Claude Code を起動する）
  • 同じ階層に ◯◯-payroll-db（台帳フォルダ）がある。中に config/・events.yaml・monthly/・employees/・変動事項入力シート.xlsx
  • 同じ階層に オンボード_構造ヒアリング.md（ヒアリング様式）と 月次運用フロー.md がある
  • Claude Code を起動して、画面のフォルダ名が正しい会社になっている（初回は「信頼する」を選ぶ）

権限: スタッフの Claude Code はエンジン（scripts/）だけ編集できない設定です。会社設定（config）・従業員台帳・入力シート・月次記録はスタッフの裁量で更新できます。

ヒアリング — 構造ヒアリングシートを CC と埋める

担当: スタッフ＋CC／所要: 30〜60分（先方確認を除く）

door で Claude Code を起動し、「◯◯社のオンボードを始めます。オンボード_構造ヒアリング.md を一緒に埋めて」と伝えます。CC が質問形式で聞いてくるので、分かる範囲で答えます。不明は空欄で構いません（バックテストで確定します）。

節聞くこと使い道
§A 会社基本情報都道府県、月平均所定労働時間、割増賃金の算定基礎に含める手当、固定的賃金の項目、毎月変動する項目、雇用保険の事業区分、36協定の特別条項、時間集計と単価の丸め、賃金規程の入手状況そのまま会社設定（company.yaml）になる
§B 規模と構成人数、雇用形態の内訳、支給グループ数、締め日・支給日、社保・雇保の加入比率アラート量の見込みと台帳作成の段取り
§C 勤怠・労働時間制度固定残業の対象と時間、所定労働時間のパターン数、法定内残業の扱い、深夜・休日の頻度残業単価チェックの設定
§D 月あたりの変動事象入退社・昇給・歩合・立替・休職・賞与の頻度照会ループの負荷と賞与月の扱い
§E 税・保険の構造住民税の納付先数、乙欄の人数、等級分布、介護保険該当者、健保の種類（協会けんぽ／組合）料率と住民税チェックの設定
§F 現行工程とデータ受領勤怠データの形式と受領日、変動連絡の受け方、現在の工数、担当者、過去のヒヤリ月次運用フローの当てはめ
§G バックテスト素材直近確定月の勤怠エクスポート、取込CSV、支給控除一覧表、従業員マスタ、住民税通知、標準報酬決定通知の有無手順⑥の準備

賃金規程・就業規則は必ず入手します。割増の算定基礎や固定的賃金の根拠はここにしかありません。未確立の会社は「法令チェックのみ・会社ルールチェックは保留」と設定に明記し、規程整備は別案件として切り出します。

会社設定 — config の「要確認」を消す

担当: スタッフ＋CC（値の解釈に迷うときだけ所長）

台帳の config/company.yaml と config/common.yaml は、配置時に「要確認」の印つきで生成されています。CC に「会社設定の要確認を一緒に潰して」と頼み、一次資料を渡しながら確定していきます。編集は CC がします。

設定一次資料注意
都道府県・健保料率・介護保険料率協会けんぽの保険料額表（該当支部・年度）生成時は熊本支部の値。福岡など他県は差し替える
雇用保険料率・事業区分厚労省の年度料率表一般／農林水産・清酒／建設
最低賃金都道府県の最低賃金（発効日つき）拠点が複数県なら従業員側の勤務地で上書きできる
締め日・支給日・保険料控除タイミング賃金規程、支給控除一覧と納入告知書の月ずれ翌月控除が前提
月平均所定労働時間・割増の算定基礎・丸め賃金規程・就業規則ヒアリング §A の答えをそのまま
36協定（特別条項の有無）36協定届上限チェックの閾値になる
権限モデル開始月運用開始月承認ゲートと必須項目検証の適用開始月

確定できたら CC に「チェックを回して」と頼み、📋の「要確認」スキャンがゼロになるまで繰り返します。

法令・通達に根拠がある値の解釈（例: どの手当を割増基礎に含めるか）で迷ったら所長へ。設定を変える権限はありますが、判断の責任まで一人で抱えないでください。

従業員台帳 — employees/ を全員分つくる

担当: スタッフ＋CC（所長の事前確認は不要。不備は機械が止める）

元資料を台帳フォルダに置き、CC に「この資料から従業員台帳を作って」と頼みます。CC が employees/ に1人1ファイルで作り、型・値域・必須項目を機械チェックします。

元資料（あるものから）

  • 給与ソフトの従業員マスタ（氏名・給与・社保情報の一覧）。過去データの移行なら前システムのエクスポート
  • 賃金テーブル、労働条件通知書・雇用契約書
  • 標準報酬月額の決定通知（直近の算定・月変）、住民税の特別徴収税額通知、扶養控除等申告書の提出状況
  • 有給休暇管理簿（付与・取得・残日数）

できあがりの確認

  • 人数がマスタと一致している（役員・非加入者も含む）
  • チェックを回して、台帳の🔴（型・値域・必須項目）がゼロ
  • 入力シートの従業員ドロップダウンに全員が出る（次の取込で自動更新）
  • 個人番号（マイナンバー）や健康情報は台帳に入れていない

途中入社・退職済みの人: 直近月に支給がある人は必ず入れます。退職者は削除せず、状態を「退職」にして残します（源泉徴収票・離職票の根拠になるため）。

バックテスト — 直近1ヶ月分で定義を確定する

担当: スタッフ＋CC／素材: ヒアリング §G

  1. 直近の確定済み月を選ぶ（例: 前月分）。その月の給与支給控除一覧表を台帳フォルダに置く。
  2. CC に「◯月分の支給控除一覧を monthly に転記して、チェックを回して」と頼む。
  3. 出てきた🔴を3つに切り分ける: 設定の誤り（会社ルールの読み違い→config を直す）／台帳の誤り（マスタの写し間違い→台帳を直す）／実際のミス（過去の給与の誤り→所長へ報告）。
  4. 「説明できない差異」がゼロになるまで繰り返す。これで会社ルールの定義が確定する。
  5. 勤怠取込がある会社は、勤怠エクスポートから取込データを作り、給与ソフトの実績と突合する（残業時間などの差分が出れば原因を特定）。

ここが一番の山です。樹尚会の例では、賃金規程の逆算（一段計算・切上げ・164h・算定基礎）で51名全員一致するまで詰め、規程に書かれていない手当の性質は所長へ論点として上げました。1ヶ月分で定義が固まれば、以後は月次の照会ループが残りの個別事情を拾います。

config を足すだけでは説明できない差異が残るとき（例: 独自の日割計算、特殊な手当ロジック）は、エンジン拡張が必要な可能性があります。ここで所長へ報告します。

レビューと運用開始

担当: 所長（＋独立レビュー）→ 運用開始後は スタッフ

レビューは2段階

種類条件見るところ
軽量レビュー会社設定（config）だけで完結したヒアリングの反映漏れ、バックテストの結果、全社共通に昇格すべきルールの見落とし
重量レビューエンジンの拡張コードが必要になった拡張が共通コアから物理的に分離されているか（必須ゲート）、専用の回帰テストがあるか

挿入位置はバックテストが確定した直後、運用開始の直前です。

運用開始

  • 初月から 仕組み編の月次7ステップどおりに回します。変動は入力シートの該当タブへ、チェックは「今月の給与チェックして」。
  • 初月は照会事項が多めに出ます。回答して入力シートに登録すると、翌月から自動照合に変わります。
  • 会社固有の判断・見つかった誤り・先方からの指摘は「判断の書庫」に入れます（顧問先名や論点は入れてよい。個人の給与額や属性は入れない）。

完了チェック — 事実で判定する

「完了しました」の言葉ではなく、次が揃っていることを確認します

準備・設定

  • door（07.給与・賞与）で Claude Code が起動し、会社名が正しく出る
  • config の「要確認」がゼロ（チェックの📋に出ない）
  • 権限モデル開始月が設定されている

台帳

  • employees/ が全員分あり、台帳の🔴がゼロ
  • 入力シート（v2）が台帳直下にあり、ドロップダウンに全員が出る
  • 有給管理簿の整備方針が決まっている（未整備なら📋として残す）

バックテスト・レビュー

  • 直近1ヶ月分で「説明できない差異」がゼロ
  • 残った論点は 確認事項.md に回答欄つきで一覧化され、所長の回答が入っている
  • レビュー（軽量／重量）が PASS。拡張コードがあるなら所長へ報告済み

運用

  • 初月の🔴ゼロ＋照会全回答で確定・納品できた
  • 担当スタッフが決まり、door の CLAUDE.md に顧客固有事項（締め日・照会先・未確立事項）が書かれている

ここまで揃えば導入完了です。以後の改善は月次の照会ループと昇格ラダー（同じ照会が2回来たらルール化）で進みます。
